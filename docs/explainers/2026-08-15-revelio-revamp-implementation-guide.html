Subject
The implementation-ready Revelio Revamp plan dated 2026-08-14

You are not mainly building a chatbot. You are building and testing a method for helping people discover worthwhile directions through conversation, real-world experiments, and remembered evidence. The software exists to make that learning loop possible.

The central design choice: OpenAI remembers what was said; Neon remembers what the product currently believes is true. The current career map is injected into every model turn so corrections beat old conversation context.

01 · What you are testing

The product hypothesis is a learning loop, not a prettier report

The old Revelio collects eight answers and produces a static result. The rebuild replaces that with an adaptive agent that keeps asking until it has enough evidence, proposes three possible directions with a reason each might fit, helps the explorer choose one provisionally, designs a real experiment, and learns from what happened when the explorer returns.

The signed-in product lives directly at /. On desktop, conversation and "Your Map" sit side by side; on phones, two tabs let the explorer switch between them without losing their draft or place. Before the map has content, it says "Your map will take shape as we talk" instead of looking blank or broken.

Reflect
Compare three paths
Pick one to test
Run and observe
Continue, switch, or form a new path
The belief bar: by September 15, you should personally feel that this is something you would pay for and continue using. The pilot then tests whether that judgment generalizes beyond you.

The method deliberately tests the daily practice behind a career image. Someone attracted to “founder,” “designer,” or “professor” should receive an experiment that exposes them to the actual work, not encouragement to pursue the title. The two unchosen paths remain parked with their original reasoning, so they can be reconsidered later rather than forgotten.

A return is defined by unfinished work, not a clock. Whenever someone opens Revelio with an experiment still waiting for an observation, their next conversation picks it up—whether they were away for an hour or a month.

02 · The three kinds of state

Do not blur identity, conversation, and product truth

OpenAI

Conversation memory

What the explorer and agent said, plus tool calls and reasoning context. One durable Conversation per user gives cross-session continuity and compaction.

Tradeoff: transcript retention and vendor coupling are accepted for the MVP.

Neon

Product memory

The current statement, profile, constraints, direction paths, experiments and observations. This versioned career map is the authoritative product record.

A Markdown projection is generated for the model; Markdown is the reading format, not the database.

Better Auth

Identity and access

Which Google account the explorer controls and which session is active. Signup is public while the founder switch is on; the server derives ownership from this verified session.

Neither the browser nor the model gets to choose a user ID.

Why the split matters: a conversation may contain an old belief. If the explorer later corrects it, the career map changes and includes a tombstone telling the model not to reuse the stale version. Conversation is evidence; the career map is current truth.

03 · Conversational writes

The agent writes as understanding develops, but interpretations are not automatically truth

Every meaningful conclusion is persisted through a narrow, typed tool before the turn finishes. The model cannot perform arbitrary database edits. It can perform semantic operations such as “record observation,” “update path,” or “mark this proposal confirmed.”

Assent stays conversational: “yes, that captures it” can cause a mark_confirmed tool call. The database calls the earlier state proposed, but the interface uses the friendlier label “Suggested.” Agreement is separate from progress: an experiment can be “Confirmed” while its progress is “Not started,” “In progress,” or “Done.” When the explorer picks one of three paths, that path becomes active and the other two are parked in the same update. There is no approval-card interface. Ambiguity should lead to another question, not an inferred acceptance.

Written immediately

  • Facts the explorer directly provides
  • Observations after an experiment
  • Agent proposals shown as Suggested
  • Conversational assent or a path pick as a status transition

Protection around every write

  • Validated operation schema
  • Expected career-map version
  • Unique source/tool-call ID
  • Atomic map update plus history entry
04 · One turn end to end

A streamed answer is only the visible surface of a transaction

  1. The browser sends only the new message, carrying a stable client message ID.
  2. Express verifies the Better Auth session and acquires that user's turn lease. A second simultaneous message gets a friendly conflict instead of racing.
  3. The server loads the latest career map and turns it into a concise request-scoped briefing.
  4. The agent runs against the user's OpenAI Conversation, with compaction enabled and bounded access to web search and map tools. Its loop uses the pinned AI SDK's standard behavior rather than a Revelio-specific rule.
  5. Each tool write is validated, version-checked, deduplicated and committed to Neon before the agent treats it as successful.
  6. The reply streams to the browser. On completion, the workspace refetches the authoritative map.
  7. The lease is released even after an error. A later request can reclaim a stale lease left by a crashed function.
Retry and interruption rule: sending the same client message ID again never invokes the model twice. A visible Stop button cancels the current reply. Sending a new message while Revelio is replying cancels the old reply first, then sends the new one—so “You seem stuck” becomes a real interruption, not a second overlapping turn.
05 · Authentication in plain English

Any Google account can sign in while signup is enabled

The rebuilt product becomes the homepage. When someone opens /, a signed-in visitor uses the chat-and-map product right there; a signed-out visitor goes to /login. The visitor chooses Google; Google proves control of the identity; Better Auth resolves or creates the Revelio user, sets the secure session cookie, and returns to /. Returning with the same Google account restores the same career map. The old anonymous questionnaire remains available at /legacy. There is no separate /explore product route, invitation allowlist, magic-link email, password flow, or Resend dependency.

The founder can pause new accounts with AUTH_SIGNUPS_ENABLED without locking out existing users. The Google project stays External + Testing for the pilot and requests only the identity scope set that Better Auth emits as openid email profile; Google's current identity-only exception allows any Google account in that configuration. A later move to public production verification requires a controlled domain, homepage, and privacy policy, but that is not a Stage 0 pilot blocker.

Better Auth uses its native PostgreSQL adapter in a separate auth schema. Revelio's Drizzle schema remains explicitly scoped to public. Authentication rate limits protect /api/auth/*. Normal agent use has no daily allowance, and replies use the pinned AI SDK's standard loop behavior. Individual text and audio requests are bounded, only one turn runs per user, billing is watched, and the agent has an emergency off-switch. The user can stop or interrupt any reply. The anonymous legacy app keeps its existing behavior until real usage justifies a targeted control.

06 · The three early proofs

Prove the external service, define the method, then test the experience

U1

Live OpenAI check

A small temporary program calls the real OpenAI service. It proves that one conversation can continue across turns, long context can be shortened, web search and Revelio's own actions work together, the private career briefing is not accidentally saved as dialogue, and the conversation can be deleted.

This answers: “Can the chosen service actually do what the architecture assumes?”

U2

Thesis and method

The thesis is the one-page belief behind Revelio: who it serves, what normal career advice gets wrong, what Revelio believes instead, and why this approach might work. The method is the ordered loop the agent follows: reflect, compare three plausible paths, pick one, test the real practice, observe, then continue, switch, or create a new path.

The agent may draft it; you decide whether it truly represents your view.

U7a

Reference conversations

Prepared example chats exercise the real model before the product machinery exists. Each example describes the situation, the behavior you expect, and what the career map should contain afterward. They test insight, adaptability, anti-prestige reasoning, three-path selection, memory writes, grounding, and response speed.

A faster model that passes these examples is preferable to a slower flagship model.

Updated web-safety decision: the dedicated malicious-webpage conversation has been removed. For this MVP, the prompt simply tells the model that search results are information, never instructions. Searches omit names, emails and raw private reflections, and search runs only when current information is actually needed. This saves build time, but it consciously accepts more risk than testing or separating web research into its own read-only step.
07 · Implementation stages

The order is designed to invalidate bad assumptions cheaply

Stage 0

Provisioning — founder

Confirm OpenAI billing and an alert, create a Google OAuth web client in External + Testing with the exact local and production callbacks, prepare Vercel secrets, and install/authenticate the Neon CLI. Better Auth is installed later with U3, when its code and migrations can be reviewed together. No Resend account, controlled domain, or OpenAI hard spend limit is required for this pilot.

Stage 1

Prove the platform and method

U1 upgrades Node 24 and AI SDK 7, cleans dead code, preserves the legacy app, and runs the real OpenAI check. U2 defines the thesis and method. U7a tests that method through reference conversations before infrastructure depends on it.

Stage 2

Build the product core

U3 adds direct Better Auth with public Google sign-in and a new-signup switch. U4 creates durable product memory. U5 connects authenticated messages, OpenAI Conversations, streaming, safe tool writes, request-size bounds, and an emergency off-switch.

Stage 3

Build and dogfood the experience

U6 supplies chat and the editable workspace. U7b integrates the validated adaptive interview. U8 completes the return-session loop.

Stage 4

Launch deliberately

U9 prepares candidates, invitation and erasure runbook in parallel. U10 applies reviewed migrations, completes the full production loop and leaves outreach ready for genuine interest.

08 · Your checkpoints

The coding agents build the mechanism; you decide whether the product deserves to exist

A

After U1: trust the provider facts?

Read the live spike. It must prove threading, compaction, search plus custom tools, non-persistent briefings and deletion. A failure changes architecture before product code is built.

B

After U7a: does the method feel distinct?

Run the reference conversations yourself. Look for adaptive curiosity, three genuinely different paths, clear reasons each might fit, anti-prestige reasoning, realistic experiments, meaningful evidence and acceptable response speed. This is the most important checkpoint.

C

After U3: can a real Google account sign in safely?

Walk the real Google flow on local port 5001. Verify first sign-in, repeat sign-in, logout, OAuth cancellation, and the signup-off rule: an unseen account is denied while an existing one still enters.

D

After U5: is conversation actually durable?

Run one live turn, inspect the map and skim redacted logs. Confirm the map write lands before the stream closes.

E

After U6 + U7b: would you use it?

Complete the entire interview as yourself. Judge the pacing, insight, friction and visible workspace—not merely correctness.

F

After U8: does returning create new value?

Come back to a seeded experiment, record what happened and see whether the next direction genuinely improves.

G

Before deploy: understand the irreversible edges

Review both Drizzle and Better Auth SQL, confirm backups, alerts, switches, callbacks and secrets, and keep the agent disabled during the first deployment.

H

At launch: make the belief judgment explicitly

Complete your production loop, enable the agent, and contact suitable candidates whenever genuine interest or a credible opportunity appears. There is no canary timer or invitation batch.

09 · What stays deliberately small

This is a protected MVP, not an enterprise platform

Build now

  • One agent route and one discovery loop
  • One flexible career-map document per user
  • Public Google identity with a signup switch
  • Persistent user/IP cost ceilings
  • Founder-run reference conversations
  • Manual pilot operation and erasure runbook

Do not build yet

  • Payments, invite gates, passwords or extra identity providers
  • Custom-domain Google production verification
  • Normalized tables for every product concept
  • Automated retention and export systems
  • Large eval or monitoring platforms
  • Weekly re-engagement and multi-loop journeys
  • Spanish UI or retirement of the old app

The safety mechanisms that remain are tied to plausible pilot failures: duplicate writes after a retry, stale data overwriting a correction, one user reaching another user's data, an oversized request, an OAuth configuration error, or a migration deleting auth tables. Billing is watched and the agent can be switched off; persistent usage quotas wait for evidence that they are needed.

10 · Tradeoffs you are consciously accepting

The architecture is optimized for speed to credible evidence

OpenAI owns the transcript

You get durable conversation state and compaction with less code. In return, sensitive reflections are retained by OpenAI until deletion, transcript retrieval depends on its API, and full erasure spans multiple systems.

The career map is flexible JSON

You can evolve the method quickly. In return, analytics and strict relational rules are weaker until the data model stabilizes.

Assent is interpreted conversationally

The product feels natural. In return, the model can misunderstand whether something is confirmed. The proposed/confirmed boundary, visible panel and reference conversations limit that risk.

The current application shell remains

You spend the month on the method and loop rather than framework migration. In return, some Express/Replit heritage survives until evidence justifies a broader rebuild.

Web-search protection is intentionally light

The model is told to treat search results as information, not instructions, and private details are kept out of queries. There is no dedicated malicious-page test or separate research step in this MVP, so this is a conscious speed-for-safety tradeoff.

Operations stay manual

Five pilots do not need dashboards and schedulers. In return, you must personally watch logs and billing alerts, execute erasure, manage outreach and notice stalled sessions.

11 · Stop conditions and common traps

Know when the plan tells the coding agent to stop

Stop and reconsider architecture

  • The real OpenAI check contradicts the Conversation or compaction assumptions.
  • AI SDK 7 materially breaks the protected legacy flow and the v6 fallback cannot preserve requirements.
  • Implementation needs an unapproved production dependency.

Do not mistake these for blockers

  • The design is not ready for hundreds of thousands of users.
  • The map schema may change after pilot learning.
  • Pilot operations require manual work.
  • The old anonymous questionnaire still exists.
  • The agent is not yet a complete career operating system.

Implementation traps worth remembering

  • Mount Better Auth before both express.json() and express.urlencoded(), or sign-in requests can hang.
  • Use local port 5001 in BETTER_AUTH_URL and the Google callback; preview URLs are signed-out-only.
  • Do not send the accumulated client transcript; send one new message and the OpenAI conversation ID.
  • Keep the per-turn career briefing out of durable conversation items.
  • Never let model tools accept a user ID or generic JSON patch.
  • Keep Better Auth in the auth schema and set Drizzle's schemaFilter to public before using db:push.
  • Reject oversized text or audio before provider work; keep the pinned AI SDK's loop default and do not add a daily allowance.
  • Forward browser cancellation through Express to the agent and tools; keep stream resumption off because it conflicts with manual Stop.
  • Do not log career text or streamed response bodies.
  • Do not run an unreviewed schema push against production.
  • Do not let the build consume U2, U7a, U9, or your dogfood time; those create the actual evidence.

  • Google Auth is External + Testing with only identity scopes; callbacks are http://localhost:5001/api/auth/callback/google and https://revelio-me.vercel.app/api/auth/callback/google.
