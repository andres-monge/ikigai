## Threat model and route/data inventory

Protect private career maps, questionnaire/audio/attachment content, conversation history, OAuth/session credentials, canonical write authority and provider spend. Relevant actors are an anonymous Internet client, a signed-in user attempting to access another user's data, untrusted model/research/file content, and a person/system with access to operational logs. A model's disagreement within its own user's map is not by itself a cross-user security failure.

## Confirmed findings

### 1. Anonymous legacy provider work has no caller-bound admission — High; recruitment blocker

**Impact / likelihood / confidence:** An arbitrary Internet client can request paid transcription and create its own legacy sessions to request generation. Easy request construction, no account prerequisite; potentially repeated provider charges and resource contention. High confidence in application sink reachability; production provider readiness, monetary impact and upstream limits remain unverified.

**Entry → sink:** [server/routes.ts:29](../../server/routes.ts#L29) mounts assessment/session/transcription outside `requireAuth`. [transcription.ts:42](../../server/routes/transcription.ts#L42) accepts anonymous audio and [line 83](../../server/routes/transcription.ts#L83) dispatches Groq. A caller can first save arbitrary valid fictional answers at [purpose-discovery.ts:180](../../server/routes/assessment/purpose-discovery.ts#L180), then reach its generation chain at [line 88](../../server/routes/assessment/purpose-discovery.ts#L88). [action-plan.ts:106](../../server/routes/assessment/action-plan.ts#L106) similarly dispatches after session/path prerequisites. The chains call AI SDK `streamText` using the configured Gemini key/model ([purpose discovery chain](../../server/ai/chains/purpose-discovery.stream.chain.ts#L45), [action-plan chain](../../server/ai/chains/action-plan.stream.chain.ts#L55), [provider factory](../../server/ai/google-structured-model.ts#L9)).

**Proof:** Three private reproduction tests use the real Express app, migrated disposable local PostgreSQL and mocked provider sinks. With `AGENT_ENABLED=false`, no cookie and no Origin, questionnaire save succeeds, both generation handlers reach their mocks, and legacy transcription returns the mock's fictional transcript. Generation mocks intentionally throw before any external work; expected 500 responses therefore prove arrival at the sink, not successful generation/billing. No production POST, paid request or load test was made.

**Existing mitigations and their limit:** JSON/body/schema validation; 5 MB legacy audio; valid prior session/path requirements; [utils.ts:24,58](../../server/routes/assessment/utils.ts#L24) has a process-local `Map` allowing one stream per caller-selected session ID. A caller can create different IDs, and different serverless instances do not share the map. Groq has no corresponding legacy concurrency guard. None of these supplies caller-bound admission. The 300-second Vercel execution limit does not establish total spend control. Production key names are present in current metadata, but key validity, provider-side caps and any separate WAF controls were not exercised or fully inventoried.

**Minimal choices for review:** If legacy is no longer needed for MVP, stop exposing its paid routes (preserving data; no deletion implied). If it must remain, establish explicit access/admission for the legacy workflow and transcription, bind resulting records to the admitted owner, and apply shared concurrency/abuse controls appropriate to that service. Authentication alone does not prevent a bot with an allowed account from parallel fan-out. Keep legitimate Method text/audio use available through its existing protected routes. Do not introduce an arbitrary daily model-call allowance or advertise Method flags as legacy containment.

**Verification after a reviewed fix:** Fixture requests without admission must stop before provider/storage creation; two fictional admitted identities must not read/replace each other's records; duplicate/parallel work must be bounded across relevant workers. Test the legitimate intended legacy/Method transcription paths separately. Build/package the exact reviewed source, then verify deployed nonmutating boundary/configuration and approved minimal legitimate usage. No production abuse simulation is needed.

### 2. Legacy logging copies private content and the session bearer into operational logs — Medium; fix with the legacy boundary batch

**Impact / likelihood / confidence:** Log readers/processors gain private transcript/content prefixes. Legacy session IDs are sufficient to read and replace assessments, so logging them also creates reusable bearer exposure beyond the browser/data store. High-confidence logging behavior; exploitation requires log access or another ID leak. No anonymous log access, session enumeration or real-user compromise was established. This is not a claim that merely presenting an intentional bearer ID is independently BOLA.

**Entry → sink:** [app.ts:95–107](../../server/app.ts#L95) captures and logs up to 120 characters of every non-Method API JSON response. `/api/transcribe` returns `{ text: … }`, so the transcript prefix goes directly into logs. Questionnaire save returns `{ sessionId, success }`; session GET logs the bearer in the URL and a hydrated-response prefix. [session.ts:24–47](../../server/routes/session.ts#L24) reads by that ID alone; [purpose-discovery.ts:194–243](../../server/routes/assessment/purpose-discovery.ts#L194) overwrites answers and removes generated content for the same ID. [ai-logger.ts:38,58,102](../../server/utils/ai-logger.ts#L38) also truncates rather than redacts questionnaire input and raw generated text on errors. Error call sites explicitly pass questionnaire answers.

**Proof:** The private fixture reads/overwrites a synthetic assessment with its known ID and asserts the ID appeared in intercepted logs; the retained local output also contains only the fictional transcription prefix. This proves the bearer and content logging sinks without reading production logs or any real records. Client IDs are generated by `Math.random()` plus time ([App.tsx:118](../../client/src/App.tsx#L118)); no practical prediction attack was attempted or claimed.

**Existing mitigation:** Method routes have a separate metadata-only logger and protected error handling, covered by passing privacy tests. Auth handling precedes this logger. Those protections do not cover legacy routes; truncation limits volume, not disclosure.

**Minimal proposal / verification:** Extend metadata-only logging to legacy success/error paths, with safe route labels instead of bearer-bearing paths and no transcript/answers/raw model output. Retiring legacy routes alone does not remove existing log copies. Review existing log access/retention without browsing user payloads. If legacy remains, address owner/admission and bearer handling together with finding 1; use cryptographic opaque values for any retained capabilities. Add sentinel-based success/error tests showing that neither bearer nor private content enters logs while legitimate read/write behavior still works. No credential rotation or bulk log deletion is authorized here.

**Recruitment disposition:** Recommended for the same legacy remediation batch; not an independent recruitment blocker or demonstrated anonymous Internet data breach. The independent assessment agreed on this distinction after reconciliation.

### 3. Pinned Better Auth PostgreSQL rate limiting falls within a concurrency-bypass advisory — Low; can wait for a reviewed dependency batch

**Impact / likelihood / confidence:** Concurrent auth requests may exceed the intended database-backed limit. This weakens abuse protection; it is not a Google identity/session forgery. Moderate confidence in deployed exposure from locked version/configuration and installed-source trace; no live auth flood or dedicated dependency-level concurrency reproduction was run.

**Entry → sink / evidence:** [auth.ts:123](../../server/auth.ts#L123) enables database rate limiting; [auth.ts:175](../../server/auth.ts#L175) supplies a direct PostgreSQL pool to Better Auth. `package-lock.json` pins `better-auth` and `@better-auth/kysely-adapter` 1.6.29 (adapter entry near line 636); installed versions match. The maintainer's [GHSA-44jh-23m7-hpcf](https://github.com/better-auth/better-auth/security/advisories/GHSA-44jh-23m7-hpcf) explicitly covers database-backed PostgreSQL with stable Kysely 1.6.x. Installed adapter `dist/index.mjs:511–545` implements the affected increment shape: selection predicates are inside the ID subquery rather than reapplied to the outer UPDATE. The package code is ignored installed evidence, not a new tracked dependency file.

**Mitigations / severity:** Google is the only enabled provider; password, Magic Link, email OTP and SSO plugins are absent. CSRF/origin/OAuth validation still apply. The advisory does not establish account takeover. Source review did not establish a separate upstream auth rate policy.

**Minimal proposal / verification:** Prepare an aligned Better Auth package/lockfile upgrade on a currently supported patched line after reviewing the pinned-version plan and release notes. Do not independently swap one transitive adapter. Run existing auth/origin/session tests plus an owned local concurrency check and actual approved Google returning-session proof on the candidate. The maintainer also [announced a security release for November 3, 2026](https://better-auth.com/blog/security-release-2026-11-03), covering 1.7.x/1.8-beta; reassess the published advisories then. That future announcement is not evidence of an additional Nami vulnerability today, and no monitor was created.

## Boundaries reviewed without a confirmed vulnerability

- **Identity/session/OAuth/CSRF/CORS:** Reviewed `auth.ts`, `auth-middleware.ts`, `auth-database.ts`, app mounting and exact-origin helpers. Google identity scopes only; caller-supplied additional scopes discarded; ID-token sign-in and implicit account linking disabled; OAuth tokens encrypted; database-backed state; HttpOnly/SameSite=Lax/Secure production cookies; own server session establishes identity. Method writes require exact origin/custom header/appropriate media before work. No permissive authenticated API CORS observed. Deterministic tests passed; fresh real OAuth callback/QA login was not run.
- **Ownership/BOLA and provider conversation boundaries:** Reviewed route→tool→storage paths. Owner IDs come from `response.locals` session identity, not model/body/query; strict turn schema rejects owner/conversation fields. Storage predicates include user ID and lease/turn identity. History cursors use AES-GCM and are rejected when minted for another conversation before provider access. Tests cover foreign/missing presentation turns, hostile owner fields, stale writes, lease conflicts, cancellation and repair. No cross-user Method read/write path found; no real account tampering attempted.
- **Attachments, paths, SSRF and parsers:** Method uses strict file types/extensions, canonical base64, byte-total bounds, magic signatures and sanitized display names. Bytes go to provider input, not a caller-controlled local filepath; no server ZIP/document extraction found. Search is provider-native, citations validate HTTPS and are display data. Provider history/audio fetches use fixed OpenAI origins and encoded IDs. No general user-URL fetch, shell tool or arbitrary filesystem tool is registered. Provider-side parsing remains outside this source audit.
- **Prompt injection and rendering:** Model tools are scoped to the runtime owner, permitted checkpoint operations, strict schemas and revision/receipt guards; no email/send/admin/cross-user action tool found. Method Markdown allowlists elements, disables arbitrary links/images/raw HTML and permits only bound safe citations. Legacy React Markdown uses no raw-HTML plugin. Chart style interpolation is developer-configured, with no user-content path found. No demonstrated XSS or research/file content crossing into another user's authority.
- **Reporting, private files and secrets:** Reporting CLI enforces target/participant choice, private-root containment, no traversal/symlinks, file permissions and manifests; no HTTP report endpoint mounted. `.vercelignore` excludes `.context`, docs, scripts and env files; package preparation/checker explicitly strips/private-audits output. A limited signature scan of 543 tracked files found no private-key/Google/OpenAI/GitHub-token signature hits. That is not an exhaustive secret-history audit. No real secret values, vault enumeration, founder data, production logs or cohort exports were inspected. Current deployed package privacy remains inherited release evidence.
- **Cost/runaway controls:** Method retains authenticated access, request/text/file/audio bounds, server-owned conversation, durable single active turn, cancellation/lease fencing, bounded history retrieval, 50-step stop and output-token ceiling. These prevent several runaway modes, not unlimited aggregate spending. Public signup and absence of a daily allowance are explicit product policy, not independent findings. Additional authenticated audio concurrency control may be useful if actual abuse appears; no unsupported numerical quota is proposed.

## Practical remediation order

1. Review the legacy product choice: remove obsolete public paid entry points, or preserve them with explicit access/admission and scoped data authority. This is the only product-direction decision needed before implementing the first batch. Include metadata-only legacy logs and transcription coverage; retain existing data.
2. Verify that anonymous calls cannot reach paid/storage work and that admitted users cannot cross owners. Preserve usable legitimate Method conversations, audio and cancellation. Review and release the exact candidate through the existing verification/package/deployment gates; no automatic release authority is implied by this report.
3. Prepare an aligned auth dependency update and complete the blocked dependency inventory when the configured advisory service works; recheck November 3's published auth advisories. Neither version matching nor this scheduled announcement establishes additional current takeover exposure.

There is no recommendation for a compliance program, new dashboard/framework, arbitrary tight model-call quota, schema reset, broad erasure exercise, key rotation, or changes to intended public signup.
